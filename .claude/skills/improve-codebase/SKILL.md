# Improve Codebase — 코드베이스 품질 개선

얕은 모듈을 깊은 모듈로 전환한다. **동작은 보존하고, 구조만 개선한다.**

---

## 핵심 개념: 얕은 모듈 vs 깊은 모듈

```
얕은 모듈 (나쁜 예)
  인터페이스: getUserDataAndValidateAndTransformAndSave(user, config, opts, cb)
  내부 구현: 10줄 — 다른 함수 3개 호출만 함

깊은 모듈 (좋은 예)
  인터페이스: saveUser(user)
  내부 구현: 100줄 — 검증·변환·저장을 모두 처리
```

**기준**: 인터페이스가 단순하고, 내부가 복잡할수록 좋다.

---

## 동작 흐름

### STEP 1: 대상 파악

`$ARGUMENTS`에 파일/디렉토리 경로가 있으면 그 범위로, 없으면 현재 디렉토리 전체.

```
📂 분석 대상: {경로}
```

### STEP 2: 얕은 모듈 감지

| 징후 | 설명 |
|------|------|
| **파라미터 과다** | 함수 파라미터 5개 이상 |
| **패스스루** | 받은 값을 그대로 다른 함수에 전달만 함 |
| **이름의 and** | `validateAndSaveUser()` — 두 가지 일 |
| **과도한 노출** | 내부 구현 세부사항이 인터페이스에 노출 |
| **얇은 래퍼** | 다른 함수를 단순 감싸기만 하는 함수 |

보고 형식:
```
🔍 얕은 모듈 감지:

  1. {파일:줄번호} — {함수명}
     문제: {파라미터 7개 / 패스스루 / ...}
     개선 방향: {구체적 제안}

  2. {파일:줄번호} — {함수명}
     ...
```

감지 결과가 없으면:
```
✅ 얕은 모듈 없음. 코드베이스가 이미 좋은 구조입니다.
```

### STEP 3: 개선 계획

발견된 모듈 중 레버리지 높은 것부터:

```
📋 개선 계획 (우선순위 순):

  P0 — {함수명} ({파일}) : {개선 방법}
       근거: 가장 많이 호출됨 / 호출 측 복잡도가 높음
  P1 — {함수명} : {개선 방법}
  P2 — {함수명} : {개선 방법}

어디서부터 시작할까요?
```

### STEP 4: 리팩토링 실행

선택된 모듈부터 순서대로:

1. 현재 코드 Read
2. 테스트 존재 확인 → 있으면 먼저 실행
3. 개선된 코드 작성
4. 동작 보존 검증 (테스트 또는 수동 확인)

**리팩토링 원칙**:
- **동작 보존** — 기능은 절대 변하지 않는다
- **한 번에 하나** — 여러 모듈 동시 리팩토링 금지
- **작은 단계** — 각 단계가 독립적으로 검증 가능해야 한다

### STEP 5: 완료 보고

```
✅ 리팩토링 완료

  {함수명}: 파라미터 7개 → 2개, 내부에서 검증·변환 처리
  {함수명}: 패스스루 제거, 직접 처리로 전환

동작 검증: {테스트 결과 또는 수동 확인}

다음 P1 리팩토링으로 이어갈까요?
```

---

## 규칙

- **동작 변경 금지** — 리팩토링은 동작을 보존한다
- 테스트 없는 코드: 리팩토링 전 기본 테스트 작성 제안
- 전체 일괄 변경 금지 — 파일/모듈 단위로
- 개선 계획은 반드시 사용자 확인 후 실행
- 개선 대상이 많아도 한 번에 최대 3개까지 계획 제시 (과부하 방지)

---

## 예시

**사용자**: `/improve-codebase src/utils/`

**improve-codebase**:
```
🔍 얕은 모듈 감지: src/utils/

  1. src/utils/user.js:23 — processUserDataForSaveOperation(userId, data, config, validate, transform, callback)
     문제: 파라미터 6개, 3가지 책임 혼재
     개선: saveUser(userId, data) — 내부에서 validate·transform 처리

  2. src/utils/api.js:45 — wrapApiCall(fn, opts)
     문제: fn을 단순 래핑만, 에러 처리만 추가하는 얇은 래퍼
     개선: 에러 처리를 각 API 함수에 직접 통합

📋 개선 계획:
  P0 — processUserDataForSaveOperation : 파라미터 축소 + 내부 통합 (5개 파일에서 호출)
  P1 — wrapApiCall : 래퍼 제거

어디서부터 시작할까요?
```
