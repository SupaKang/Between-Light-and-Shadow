# 108: 음양견문록 — ROM 관찰 기반 재구축 개발 보고서

문서 상태: v1.0 / 신규 개발 기준선

## 1. 경영 요약

이전 개발의 실패 원인은 게임의 외형 요소만 흉내 내고, 실제 플레이 감각을 결정하는 입력 우선순위·화면 비율·상태 전이·상호작용 규칙·피드백을 먼저 검증하지 않았기 때문이다. 결과적으로 실행은 되지만 1990년대 휴대용 RPG의 기본 품질인 “무엇을 눌렀을 때 무엇이 일어나는지 예측 가능한 경험”을 제공하지 못했다.

이번에는 제공 ROM을 **플레이 경험의 관찰 기준과 테스트 오라클**로 사용한다. 단, ROM의 코드·그래픽·음악·문자·맵 데이터는 게임에 이식하거나 재배포하지 않는다. `Gen2Recomped`도 기반 코드로 복사하지 않고, 데이터 분리·스크립트 VM·맵 이벤트·회귀 테스트 구조만 참고한다.

목표는 Pokémon을 복제하는 것이 아니라 다음 수준의 완성도를 확보하는 것이다.

- 입력이 즉시 반응하고 우선순위가 일관됨
- 캐릭터·카메라·충돌·상호작용 기준점이 안정적임
- 대화·메뉴·전투의 UI 위치와 흐름이 예측 가능함
- 플레이어가 탐험 → 조우 → 전투 → 계약 → 관리 루프를 자연스럽게 학습함
- 첫 30분이 처음부터 끝까지 실제로 플레이 가능함

## 2. 기존 실패를 방지하는 개발 원칙

### 원칙 A — 화면보다 상호작용을 먼저 검증

아트 제작이나 108종 데이터보다 먼저 회색 박스 프로토타입으로 이동, 조사, 대화, 메뉴, 전투를 검증한다.

### 원칙 B — 모든 관찰은 측정값으로 기록

“비슷해 보인다”를 기준으로 삼지 않는다. ROM 플레이 관찰에서 다음을 표로 기록한다.

- 화면 해상도와 논리 좌표
- 플레이어 이동 단위와 이동 속도
- 입력 반복·키다운·확인·취소 우선순위
- 대화창 위치·줄 수·페이지 넘김 규칙
- 메뉴 열림/닫힘과 커서 이동 규칙
- NPC 접촉 방향과 상호작용 거리
- 맵 경계·문·계단·워프 판정
- 전투 명령 선택·취소·턴 처리·결과 표시 순서

### 원칙 C — 한 번에 한 시스템만 이식

이동 검증이 끝나기 전에 전투와 도감에 들어가지 않는다. 각 단계는 플레이 영상 또는 입력 로그와 자동 회귀 테스트를 남긴다.

### 원칙 D — 콘텐츠와 엔진을 분리

엔진은 독자적으로 작성하고, 요괴·기술·아이템·맵·대화는 데이터 파일로 주입한다. 이 구조가 있어야 나중에 ROM과 다른 `108`의 규칙을 안전하게 개선할 수 있다.

## 3. ROM 관찰 랩

### 3.1 관찰 환경

- 합법적으로 보유한 ROM만 로컬에서 사용
- 에뮬레이터의 프레임 진행, 입력 표시, 메모리/화면 캡처 기능 활용
- ROM 파일은 프로젝트 저장소에 복사하지 않음
- 원본 데이터 추출물은 게임 에셋으로 커밋하지 않음
- 관찰 결과는 좌표·상태·행동 규칙 같은 사실만 문서화

### 3.2 관찰 시나리오

1. 부팅부터 타이틀까지
2. 새 게임 시작과 초기 설정
3. 첫 방에서 이동·조사·출구
4. NPC 대화·선택지·대화 종료
5. 마을 메뉴·가방·파티 화면
6. 필드 이동·충돌·문·계단·맵 전환
7. 야생 조우와 전투 명령
8. 아이템 사용·교체·도주·전투 종료
9. 저장·재시작·저장 데이터 복원

각 시나리오에는 `입력 → 화면 상태 → 기대 결과 → 관찰 결과 → 차이 → 수정 커밋`을 기록한다.

## 5. 단계별 개발 계획

### Phase 0 — 기준선 조사

산출물: `ROM_OBSERVATION_LOG.md`, 입력 매핑표, 화면 좌표표, 상태 전이표

완료 조건: 첫 30분 플레이의 모든 입력과 결과를 재현 가능한 테스트 케이스로 표현함.

### Phase 1 — 회색 박스 입력·월드

- Full HD 창과 960×540 논리 프레임버퍼
- 32×32 타일 그리드
- 4방향 이동과 정지
- 충돌·맵 경계·카메라 추적
- 확인·취소·메뉴 입력

완료 조건: 10분 동안 이동해도 미끄러짐·대각선 오입력·카메라 떨림·벽 통과가 없음.

### Phase 2 — 상호작용·대화

- NPC 접촉 및 조사 포인트
- 대화창 고정 앵커
- 페이지 넘김·대화 종료·선택지
- 이벤트 플래그와 맵 전환

완료 조건: 집 → 마을 → 필드 → NPC → 출구 흐름을 저장 없이 완주.

### Phase 3 — 메뉴·저장

- 시작 메뉴
- 파티·도감·유물 화면
- 커서 이동과 취소 스택
- 저장·로드·손상 파일 처리

완료 조건: 어느 메뉴에서든 취소하면 이전 상태로 정확히 돌아오고, 저장 후 재실행해 플래그가 복원됨.

### Phase 4 — 전투 뼈대

- 조우 전환
- 1v1 턴 상태 머신
- 기술·교체·도주·계약 명령
- HP/Qi·턴 순서·승패·결과 화면

완료 조건: 회색 박스만으로도 전투 10회 연속 완료 가능.

### Phase 5 — 첫 Vertical Slice

- 고품질 아트가 적용된 마을 1개
- 필드 1개
- NPC 3명
- 요괴 3종
- 기술 6개
- 유물 2개
- 메인 목표 1개와 단발 퀘스트 1개

완료 조건: 신규 플레이어가 안내 없이 20~40분 플레이하고, 입력·UI·목표·계약 흐름에서 막히지 않음.

### Phase 6 — 콘텐츠 확장

검증된 엔진 위에 지역·요괴·기술·아이템·퀘스트를 데이터로 추가한다. 108종은 마지막에 확장한다.

## 6. 화면 및 입력 품질 기준

### Full HD 기준

- 출력: 1920×1080
- 논리 화면: 960×540
- 정수 배율: 2배
- UI 앵커는 논리 좌표로 저장
- 모든 픽셀 아트 확대는 nearest-neighbor

### 입력 기준

- 한 프레임에 방향 입력 1개만 이동 명령으로 확정
- 확인 입력은 현재 상태가 소비하지 않으면 상위 상태로 전달하지 않음
- 취소는 메뉴 스택을 한 단계만 되돌림
- 대화 중 이동 입력은 무시
- 전투 연출 중 명령 입력은 버퍼링하지 않음
- 키보드와 컨트롤러는 동일한 논리 명령으로 변환

## 7. ROM 기반 뼈대와 `108` 개선의 경계

### 가져올 것

- 화면·입력·상호작용을 관찰하는 방법
- 타일·메타타일·맵 이벤트를 분리하는 개념
- 상태 머신 기반 대화·메뉴·전투 구조
- 입력 트레이스와 화면 회귀 테스트 방식
- 데이터 ID 기반 저장 구조

### 가져오지 않을 것

- ROM 코드·디스어셈블 결과·바이너리
- 원본 그래픽·음악·문자·맵·캐릭터
- 원본 게임의 상표·고유 명칭·스토리·수치 테이블
- 원본 ROM을 요구하는 런타임 구조

## 8. 품질 보증 체계

각 기능은 다음 네 가지 테스트를 모두 통과해야 한다.

1. **입력 테스트**: 키 입력과 컨트롤러 입력 결과가 동일함
2. **상태 테스트**: 장면·플래그·저장 데이터 전이가 정확함
3. **화면 테스트**: 기준 해상도에서 좌표·창·커서·스프라이트가 안정적임
4. **플레이 테스트**: 처음부터 실제 목적을 달성할 수 있음

스크린샷 비교는 색상 픽셀 전체 일치보다 UI 앵커, 플레이어 위치, 커서 위치, 창 크기, 상태 텍스트 영역을 우선 비교한다.

## 9. 첫 구현 작업 목록

1. 코드 없는 현재 저장소에 새 빌드 골격 생성
2. Full HD 창과 960×540 논리 렌더러 작성
3. 입력 명령 큐와 취소 스택 작성
4. 회색 박스 마을·집·필드 맵 작성
5. 플레이어 충돌·카메라·NPC 상호작용 작성
6. ROM 관찰 로그의 첫 10개 입력 시나리오를 자동 테스트로 변환
7. 그 후에만 주인공·NPC·요괴 아트 제작 시작

## 10. 성공 기준

“실행된다”가 아니라 다음을 만족해야 Phase 1을 통과한다.

- 신규 플레이어가 방향키와 확인/취소만으로 첫 필드에 도달
- 캐릭터가 모든 벽과 경계에서 정확히 멈춤
- NPC·출구·조사물의 상호작용 범위가 예측 가능
- 대화창과 메뉴가 항상 같은 위치·크기·입력 규칙을 가짐
- 전투 진입과 종료 후 위치·상태가 보존됨
- 30분 플레이 중 소프트락이 없음
- 기준 시나리오의 입력 트레이스가 매 빌드 동일한 결과를 냄
