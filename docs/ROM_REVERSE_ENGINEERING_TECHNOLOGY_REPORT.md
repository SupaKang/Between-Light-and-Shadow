# GBC ROM 코드 이해 기술 조사 보고서

## 1. 결론

GBC ROM을 코드 수준으로 분석하는 기술은 존재한다. 다만 ROM은 원본 C/C++ 소스가 아니라 CPU 명령어, 그래픽 데이터, 테이블, 스크립트, 압축 데이터가 섞인 바이너리이므로 다음 네 가지 분석을 병행해야 한다.

```text
정적 분석       디스어셈블·뱅크·심볼·데이터 경계 파악
동적 분석       에뮬레이터 디버거·브레이크포인트·메모리 추적
그래픽 분석     VRAM·타일·팔레트·OAM·맵 블록 분석
행동 분석       입력 로그·상태 변화·화면 캡처·회귀 비교
```

이 결과를 이용하면 `108`에 필요한 “플레이 가능한 뼈대”를 훨씬 정확하게 설계할 수 있다. 단, 분석 결과를 원본 코드·에셋으로 재사용하는 방식은 사용하지 않는다.

## 2. 확인된 주요 기술

### 2.1 RGBDS 및 어셈블리 빌드 체계

RGBDS는 Game Boy/Game Boy Color용 어셈블러·링커·그래픽 변환 도구 모음이다. RGBASM으로 소스 어셈블, RGBLINK로 ROM 링크, RGBGFX로 그래픽 변환, RGBFIX로 ROM 헤더를 정리할 수 있다. [RGBDS 공식 사이트](https://rgbds.gbdev.io/)

원본 ROM 분석에서는 디스어셈블된 코드를 다시 빌드할 때 사용하며, `108`의 최종 엔진은 반드시 별도 C++ 또는 독자 런타임으로 작성한다.

### 2.2 Pokémon Gold/Silver 공개 디스어셈블

`pret/pokegold`는 Pokémon Gold/Silver 디스어셈블 프로젝트로, `engine`, `data`, `gfx`, `maps`, `ram`, `constants`, `audio` 등이 분리되어 있다. `main.asm`도 여러 ROM bank에 엔진·이벤트·맵·데이터 모듈을 나누는 구조를 보여준다. [pret/pokegold](https://github.com/pret/pokegold)

이 프로젝트는 다음 구조를 이해하는 참고 자료로 사용할 수 있다.

- ROM bank 배치
- RAM 변수와 플래그
- 맵·NPC·이벤트 분리
- 전투·메뉴·오디오 모듈 분리
- 심볼 이름을 통한 명령어 의미 복원

그러나 한국어 ROM과 US ROM은 버전·패치·주소·데이터 배치가 다를 수 있으므로, 심볼을 그대로 적용하지 않고 대상 ROM과 일치하는지 검증해야 한다.

### 2.3 BGB 디버거

BGB는 Windows용 Game Boy/Game Boy Color 에뮬레이터 겸 디버거다. 명령어 단위 추적, 실행·접근 브레이크포인트, VRAM viewer, I/O map, 메모리 조사, joypad 디버깅을 제공한다. [BGB 매뉴얼](https://bgb.bircd.org/manual.html)

관찰에 특히 유용한 기능:

- 현재 PC가 실행 중인 CPU 주소 확인
- 특정 RAM 주소의 읽기/쓰기 중단
- VRAM에 어떤 타일이 로드되는지 확인
- 버튼 입력 직후 실행 경로 추적
- 전투 진입·메뉴 열기·맵 전환 시점의 상태 변화 기록

### 2.4 mGBA 계열 디버깅

mGBA는 주로 GBA 에뮬레이터로 알려져 있지만 디버거·명령줄 도구·개발용 기능을 제공한다. GBC 관찰은 BGB가 더 직접적이며, mGBA는 자동화나 다른 플랫폼 검증이 필요할 때 보조 후보로 둔다. [mGBA 저장소/문서](https://github.com/mgba-emu/mgba)

## 3. 권장 분석 도구 조합

```text
BGB 또는 SameBoy       실제 플레이·브레이크포인트·VRAM 관찰
Hex editor              ROM bank·바이트·포인터 확인
RGBDS                  어셈블리/심볼/재빌드 참고
Tile viewer             2bpp/4bpp 타일과 팔레트 확인
Python                  반복 스캔·해시·포인터·로그 자동화
Ghidra                  보조 디스어셈블 및 그래프 확인
```

Ghidra는 일반적인 x86 프로그램처럼 자동으로 의미 있는 소스를 복원해 주지 않는다. GBZ80 명령어 프로세서 정의, bank 전환, 코드/데이터 경계 수동 지정이 필요하므로 주 도구가 아니라 보조 도구로 사용한다.

## 4. 분석 절차

### Step 1 — ROM 식별

- 파일 크기, SHA-256/SHA-1
- 헤더 타이틀, CGB 플래그
- 카트리지 타입, ROM/RAM 크기
- 알려진 디스어셈블·재현 프로젝트의 지원 버전과 비교

### Step 2 — bank 지도 작성

- 32KiB bank 단위로 파일 분할 관찰
- 고정 bank와 전환 bank 구분
- 반복되는 포인터·점프 테이블 탐색
- 코드 영역과 그래픽/문자/맵 데이터 후보 분리

### Step 3 — 실행 진입점 추적

- 부팅 벡터에서 초기화 루틴 추적
- 입력 처리 루틴 찾기
- 현재 화면과 맵이 바뀌는 지점에 브레이크포인트 설정
- RAM 변수 변화를 입력 시나리오와 함께 기록

### Step 4 — 화면·그래픽 분석

- VRAM viewer로 타일 로딩 확인
- 배경 tilemap과 OAM 스프라이트 구분
- 팔레트 변경 타이밍 기록
- 대화창·메뉴·전투 HUD의 화면 좌표 측정

### Step 5 — 이벤트·상태 분석

- NPC 접촉·확인 버튼·출구 이벤트 추적
- 이벤트 플래그의 설정·검사·초기화 기록
- 맵 전환 전후 좌표와 방향 기록
- 전투 진입·명령·결과·복귀 상태 기록

### Step 6 — 입력 회귀 데이터 생성

각 시나리오를 다음처럼 저장한다.

```json
{
  "scenario": "first_village_npc",
  "inputs": ["START", "DOWN", "DOWN", "A"],
  "checkpoints": [
    {"frame": 120, "screen": "village", "player_tile": [7, 5]},
    {"frame": 180, "screen": "dialogue", "cursor": null}
  ],
  "status": "VERIFY"
}
```

## 5. `108` 개발로 변환하는 방법

ROM의 실행 경로를 그대로 포팅하지 않고, 관찰 결과를 다음 독자 시스템으로 변환한다.

| 관찰 결과 | `108` 독자 구현 |
|---|---|
| 입력이 한 번 이동함 | `InputCommand::Move(direction)` |
| 확인 버튼이 NPC 대화를 시작함 | `InteractionResolver` |
| 맵 전환 후 새 위치에 배치됨 | `WarpEvent` 데이터 |
| 대화가 여러 페이지로 진행됨 | `DialogueStateMachine` |
| 메뉴에서 하위 화면으로 이동함 | `SceneStack` |
| 전투 명령 후 턴이 실행됨 | `BattleStateMachine` |
| RAM 플래그가 바뀜 | `StoryFlag` 저장 테이블 |
| VRAM 타일이 바뀜 | `TileSet`·`SpriteSheet` 런타임 리소스 |

## 6. 반드시 분리해야 할 것

### 참고 가능

- 입력 우선순위
- 화면 전환 순서
- 커서 이동 규칙
- 맵·이벤트·전투의 상태 머신 개념
- 타일·스프라이트·팔레트의 저장 방식
- 회귀 테스트 절차

### 이식 금지

- ROM의 어셈블리 코드
- ROM에서 추출한 그래픽·음악·문자
- 원본 맵·NPC·대사·전투 수치
- 원본 상표·캐릭터·고유 명칭
- 저작권이 제한된 디스어셈블 파일의 무단 재배포

## 7. 우리 프로젝트에 대한 기술 판단

현재 프로젝트는 코드가 삭제된 상태이므로, ROM 분석 도구를 먼저 별도 폴더에 설치하고 관찰 산출물만 `docs/observation/`에 저장하는 것이 적합하다. 게임 런타임은 ROM 임포터가 아니라 독자 데이터와 독자 아트를 읽어야 한다.

권장 순서는 다음과 같다.

1. BGB에서 ROM 부팅과 첫 화면 관찰
2. 첫 30분 입력 로그와 화면 캡처 확보
3. 이동·대화·메뉴·맵 전환 명세 작성
4. 회색 박스 C++ 런타임 구현
5. 기준 입력 로그를 자동 회귀 테스트로 변환
6. `108` 고유 콘텐츠와 아트 통합

## 8. 결론

ROM을 코드 수준으로 이해하는 것은 가능하지만, 자동 디컴파일 한 번으로 완성된 게임 소스를 얻는 기술은 아니다. 가장 신뢰할 수 있는 방법은 `BGB 동적 디버깅 + 공개 디스어셈블 구조 참고 + 직접 작성한 관찰 자동화 + 독자 런타임 재구축`의 조합이다.

이 접근을 택하면 이전처럼 화면만 흉내 낸 프로그램이 아니라, 입력·상태·UI·상호작용이 검증된 90년대식 플레이 뼈대를 먼저 만들 수 있다.
