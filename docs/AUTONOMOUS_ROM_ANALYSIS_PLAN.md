# 자율 ROM 분석 및 재구축 계획

## 1. 변경 이유

기존 계획은 사용자가 VBA를 직접 조작하고 화면을 캡처해야 한다는 의존성이 있었다. 이 방식은 진행이 느리고, 관찰 자료의 누락·측정 오차·재현 불가능성이 생긴다.

새 계획에서는 사용자의 조작을 요구하지 않는다. 로컬 ROM 파일을 입력으로 받아 분석 도구가 자동으로 구조를 추출하고, 그 결과를 독자 엔진의 설계 입력으로 변환한다.

## 2. 핵심 전략

```text
ROM 파일
  ↓
자동 식별·무결성 검사
  ↓
bank 지도·코드 후보·포인터·타일·팔레트 탐색
  ↓
공개 디스어셈블·심볼과 교차 대조
  ↓
기능별 구조 보고서 생성
  ↓
108 독자 데이터 모델과 회색 박스 엔진 작성
  ↓
자동 시나리오 테스트
```

핵심은 원본 게임의 코드를 이식하는 것이 아니라, ROM에서 **행동 구조를 증거 기반으로 추론**하고 같은 역할의 `108` 전용 코드를 새로 작성하는 것이다.

## 3. 자동 분석 단계

### 단계 A — ROM 식별

자동으로 기록한다.

- 파일 크기와 bank 수
- 헤더 타이틀·CGB 플래그·카트리지 타입
- ROM/RAM 크기
- SHA-256/SHA-1
- 알려진 디스어셈블 버전과 일치 여부

불일치하면 해당 공개 심볼을 직접 적용하지 않고 `VERIFY`로 표시한다.

### 단계 B — bank 구조 분석

각 16KiB/32KiB 영역별로 다음을 계산한다.

- 명령어로 해석 가능한 바이트 분포
- 반복 바이트·압축 후보
- 포인터 후보
- 점프 테이블 후보
- 타일 데이터 후보
- ASCII/문자 테이블 후보
- 헤더·그래픽·맵 데이터 후보

결과는 `rom_bank_map.json`과 사람이 읽는 Markdown으로 저장한다.

### 단계 C — 코드 후보 디스어셈블

Game Boy CPU 명령어 표를 이용해 bank별 바이트를 LR35902/GBZ80 명령어 후보로 변환한다. 자동 결과에는 다음을 붙인다.

- bank 번호
- ROM 파일 오프셋
- CPU 주소 후보
- 명령어
- 참조 대상
- 코드/데이터 신뢰도

데이터 안의 바이트를 코드로 오인할 수 있으므로 자동 디스어셈블을 완성된 소스로 취급하지 않는다.

### 단계 D — 함수와 테이블 추론

다음 패턴을 탐색한다.

- `CALL`, `JP`, `JR`, `RET` 흐름
- 주소 테이블과 간접 점프
- 메뉴 커서 처리 루틴 후보
- joypad 입력 상수와 비교 패턴
- VRAM/OAM/팔레트 레지스터 접근
- 맵 전환·이벤트 플래그 접근
- 전투 명령과 숫자 테이블 후보

함수 이름은 원본 명칭이 아니라 `bank03_callgraph_014` 같은 중립 ID를 사용한다.

### 단계 E — 그래픽 데이터 탐색

자동 도구로 다음을 시도한다.

- 2bpp/4bpp 8×8 타일 후보 변환
- 16×16·32×32·48×48 조합 후보 생성
- 팔레트 후보와 빈도 계산
- 반복 타일·미러 타일 탐색
- 타일맵·메타타일 후보 추출

추출 이미지는 분석용 임시 산출물일 뿐 `108` 에셋으로 사용하지 않는다.

### 단계 F — 문자열·스크립트 후보

- 가변 길이 문자열 후보
- 문자 인코딩 테이블 후보
- 이벤트 명령 바이트의 반복 패턴
- 대화·메뉴·전투 로그의 호출 관계

문자열은 원본 콘텐츠를 복사하기 위한 것이 아니라 대화 시스템의 길이·페이지·호출 구조를 이해하기 위한 분석 자료로만 사용한다.

## 4. 사용자 조작 없이 플레이 구조를 재현하는 방법

실제 에뮬레이터 입력 대신 다음을 자동 생성한다.

### 4.1 입력 모델

ROM에서 joypad 읽기 후보와 상태 분기 후보를 찾고, 이를 일반 명령으로 변환한다.

```text
UP / DOWN / LEFT / RIGHT
A / B / START / SELECT
```

### 4.2 화면 모델

VRAM/OAM/스크롤 레지스터·타일맵 쓰기 후보를 이용해 다음 화면 구성의 후보를 만든다.

- 타이틀
- 필드
- 메뉴
- 대화
- 전투

좌표가 확정되지 않는 경우에는 바이트 접근 순서와 화면 구성 후보를 함께 기록한다.

### 4.3 상태 모델

RAM 접근 후보와 분기 패턴에서 다음을 추론한다.

- 현재 맵
- 플레이어 좌표
- 방향
- 파티/생물 상태
- 아이템
- 이벤트 플래그
- 전투 단계

추론값에는 반드시 `observed`, `inferred`, `unknown` 상태를 붙인다.

## 5. `108` 변환 규칙

| ROM 분석 결과 | `108` 독자 구현 |
|---|---|
| joypad 처리 | `InputCommand` |
| 맵 이동 루틴 | `WorldMovementSystem` |
| 충돌 판정 후보 | `CollisionGrid` |
| 이벤트 호출 구조 | `EventScriptVM` |
| 대화 문자열 호출 | `DialogueStateMachine` |
| 메뉴 커서 루틴 | `MenuStateMachine` |
| 전투 단계 분기 | `BattleStateMachine` |
| 플래그 접근 | `StoryFlagStore` |
| VRAM 타일 로딩 | `TileAssetLoader` |
| RAM 저장 구조 | `SaveSchema` |

원본 함수 이름·주소·데이터를 `108` 코드에 노출하지 않는다. 분석 리포트와 게임 소스의 경계를 분리한다.

## 6. 새 프로젝트 구조

```text
analysis/
 ├─ rom_input/          원본 경로 참조만 기록, ROM 복사 금지
 ├─ reports/            bank_map, code_map, graphics_map
 ├─ inferred/           중립 ID 기반 추론 데이터
 └─ fixtures/           테스트용 합성 입력·타일·맵

runtime/
 ├─ platform/            Win32 입력·창
 ├─ render/              960x540 논리 화면·1920x1080 출력
 ├─ world/               맵·충돌·이벤트
 ├─ dialogue/            대화·선택지
 ├─ battle/              전투 상태 머신
 ├─ content/             108 전용 데이터
 └─ save/                저장·로드
```

## 8. 검증 체계

### 확정

파일 해시, 파일 크기, 헤더 바이트, 반복 패턴, 명령어 디코딩 결과처럼 바이너리에서 직접 계산되는 값.

### 추론

코드 후보, 함수 경계, 포인터 테이블, 화면 역할처럼 패턴을 해석한 값.

### 미확정

실제 프레임 타이밍, 플레이어가 보는 최종 화면, 특정 이벤트의 체감 동작.

추론값을 확정값으로 승격하려면 최소 두 개의 독립 증거가 필요하다. 예를 들어 코드 참조와 그래픽 쓰기 패턴이 동시에 일치해야 화면 요소로 분류한다.

## 9. 실제 진행 순서

1. Python 기반 ROM 분석기 작성
2. 제공 ROM fingerprint와 bank map 생성
3. GBZ80 디코더와 코드 후보 보고서 생성
4. 2bpp/4bpp 타일 후보 시트 생성
5. 입력·화면·상태 추론 보고서 작성
6. 108 전용 Full HD 회색 박스 런타임 작성
7. 자동 입력 시나리오로 이동·대화·전투 상태 검증
8. 검증된 런타임에 독자 아트와 콘텐츠 통합

## 10. 한계와 판단

정적 분석만으로는 “실제 플레이 화면을 100% 재현”할 수 없다. 특히 압축 해제 시점, 간접 점프, 동적 타일 로딩, 프레임 타이밍은 동적 디버깅이 더 정확하다.

그러나 사용자의 조작 없이도 다음은 충분히 자동화할 수 있다.

- ROM 구조 파악
- 코드·데이터 후보 분리
- 타일·팔레트·맵 후보 확인
- 입력·메뉴·이벤트·전투의 구조 추론
- `108`의 독자 엔진 계약과 테스트 설계

따라서 앞으로는 에뮬레이터 조작을 전제하지 않고, 정적 분석을 기본 경로로 삼는다. 필요한 경우에만 에뮬레이터 디버거를 보조 증거로 사용한다.
